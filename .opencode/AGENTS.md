# 项目指令 (Project Rules)

## 🇨🇳 中文回复规则（最高优先级）

**所有对话输出必须使用中文（简体中文）**：
- 思考过程与推理
- 解释与讨论
- 代码注释（除非团队规范要求英文）
- Git 提交信息
- 错误说明

例外：代码本身（变量名、函数名）遵循项目规范；URL/技术标识符保持原样。

---

## 文档维护规则

**核心原则**：每次代码改动如果改变了用户或未来开发者的使用预期，必须同步更新文档。

### ✅ 必须更新文档

- **架构调整**（新增/删除服务、数据流变更）：更新 `docs/PROJECT_ARCHITECTURE.md` + 相关设计文档
- **新增配置项**：更新 `docs/` 相关 spec + 示例配置
- **API 变更**（新增/修改路由）：更新 `docs/PROJECT_ARCHITECTURE.md` API 表
- **新增子模块**：创建新文档 + 更新索引

### ❌ 不需要更新文档

- **修复 Bug**：行为修正
- **重构**：不改行为的内部调整
- **样式调整**：纯 UI 或日志格式

### ✍️ 提交前自检

每次 `git commit` 前，必须自检：
> "这次改动是否改变了使用预期？"
> * 是 -> 同步更新文档
> * 否 -> 不需要

---

## 方案确认流程（强制执行）

**核心原则**：任何涉及架构调整、新功能实现、性能优化的方案，必须经过用户明确确认后才能实施。

### 🚫 禁止行为

- 未经用户确认直接开始实现代码
- 假设用户意图并自行选择方案
- 在用户未明确回复"确认"、"执行"、"开始"等指令前动手

### ✅ 必须执行的流程

1. **提出问题**：发现需要解决的架构/功能问题
2. **分析方案**：提供 2-3 种可行方案，包含优缺点对比
3. **等待确认**：明确询问用户选择哪个方案
4. **收到确认**：用户明确回复方案选择（如"方案 A"、"用方案 B"、"确认执行"）
5. **开始实施**：仅在收到确认后开始编码

### 📋 确认示例

**正确流程**：
```
AI: 我发现了问题 X，有 3 种解决方案... 你选择哪个？
用户: 方案 A
AI: 好的，开始实施方案 A...
```

**错误流程**：
```
AI: 我发现了问题 X，有 3 种解决方案... 我先实施方案 A
用户: （未确认）
AI: （直接开始写代码）← 禁止
```

### ⚠️ 适用范围

以下场景必须走确认流程：
- 新增功能/模块
- 架构调整（数据流变更、服务依赖变更）
- 性能优化方案选择
- 数据库 Schema 变更
- 第三方依赖引入
- 配置结构变更

以下场景可直接实施：
- 修复明确的 Bug（用户已描述问题现象）
- 代码重构（不改变行为）
- 文档更新
- 测试用例补充
